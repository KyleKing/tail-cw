# Review after a week of use, 2026-08-31

**Method.** Two passes. The first mined every Claude Code transcript under
`~/.claude/projects` for real invocations, excluding sessions inside this checkout,
which
found 75 runs across six project directories.
The second drove the app in a real pty
through tmux at 40x10, 60x20, 80x24, 120x40, and 140x44, with and without `NO_COLOR`,
capturing the log view, the `?` overlay, the histogram, the record detail, and the
dashboard with a chart staged.
Colour claims below are contrast ratios computed from the
escape sequences tmux captured, not impressions.

## What a week of use actually shows

Every one of the 75 invocations was `tail-cw export`.
Not one drove the TUI, which is
expected, because the callers were agents.
The number worth acting on is that 74 of the
75 commands were textually distinct: there is no settled idiom, each question got a
freshly assembled pipeline.

Three patterns repeat inside those pipelines, and each one is the tool handing back work
it already did.

**The structured payload arrives as a string.** Roughly a third of the runs pipe into
`jq -rc '.message | (fromjson? // empty) | select(.event=="http_request") | [...] | @tsv'`
or an inline `python3 -c` that does the same by hand.
`LogEvent.message` is a raw string
and `_event_to_record` serializes it as one, so the caller re-parses per line.
The cache
already holds the decoded payload as a `parsed` struct, which is what makes
`level:error`
work, and the export boundary throws it away.
Emitting it (behind `--parsed`, or as a
second key so nothing existing breaks) costs no new dependency and deletes the
`fromjson`
step from every future pipeline.

**Counting by a field is written out longhand every time.** Several runs end in
`collections.Counter()` over a projected field, or `sort | uniq -c | sort -rn`, to
answer
"how many of each outcome" or "which obligations failed".
DuckDB is already in the
process and already pointed at the cached Parquet.
An `export stats <group> --by parsed.status --by parsed.outcome` that groups and counts
locally would replace the
longhand, run on cached data for free, and stay inside the one-code-path rule because
the
TUI's report screen wants the same function.

**`| head -N` truncates after the whole window is paid for.** There is no `--limit` on
`export logs`, so the caller fetches the full window, writes it to Parquet, and then
SIGPIPEs the reader.
Two runs wrapped the command in `timeout 100`, which is the same
symptom.
A `--limit` that stops the fetch is the cheap fix; a `--limit` that only trims
output is not worth adding.

Three smaller frictions show up in the same corpus.

`--profile read-prod` appears on nearly every command.
Config has `[cache]`, `[fetch]`,
`[insights]`, `[message]`, `[preview]`, `[tui]`, `[trace]`, `[presets]`, and
`[filters]`,
and no place to say which profile to use by default.
A `profile` key, and a per-preset
override so `@api` can carry its own account, removes the most-typed argument in the
corpus.

`export logs` takes one group where `export summary` takes a glob, so the two commands
disagree about their own positional argument.
Callers worked around it by naming a single
group and never asking a cross-group question through `export logs`.

`export logs --demo` produces nothing, because `--demo` reached `logs`, `tail`, and
`dash` but not `export`.
There is no offline smoke test for the surface every caller
actually uses.

The Parquet dtype abort already at the top of the roadmap is confirmed by this corpus
rather than merely reported in it: the failing 72-hour fetch and the succeeding
one-hour fetch of the same group are both in the transcripts.

## The dtype abort wants a decision, and here is one

The roadmap frames the choice and stops.
Recommend repairing the inferred schema before
`sink_parquet`, which keeps the verbatim-splice hot path, and treating the two shapes
differently.
A zero-field struct is dropped, because it carries nothing.
A key inferred
as two scalar types is widened to text, and the widened paths are recorded on the
result so the caller can be told.

That trades the stated position (silently dropping a payload key is worse than failing)
for a weaker one: silently *retyping* a payload key is better than failing, provided it
is not silent.
A widened key is still searchable and still visible in the record detail,
where a failed fetch returns nothing at all.
Saying which keys were widened is what keeps
it honest, and is the part that must not be skipped.

## Terminal review

Verdict on the four questions. Progressive disclosure is well designed and then
undermined by its own reference panel.
Small terminals are handled well in the log view
and badly in the dashboard.
Previews show both the raw and the parsed payload but
highlight neither.
The palette is pleasant except where it matters most, which is the
error row.

### P0 — A staged chart has no minimum height

At 80x24 the focused chart gets four rows, and plotext fills them with axis furniture
and
no data: the plot area is empty and the y axis reads `676.8` above `1353.6`, inverted.
The
same chart at 140x44 is correct. So the app's headline feature renders as an empty box
with a backwards axis at the most common terminal size, and nothing says the pane is too
short.
Either reserve a floor for the stage and shrink the grid above it, or refuse to
stage below that floor and say why.

### P1 — The `?` overlay fits no terminal and does not scroll

At 80x24 the panel starts on row 1, runs past row 24, and is cut off at `[ [/] Prev`.
The
entire `Commands` half is unreachable, and so is the `esc to close` line the last critique
singled out as the right touch.
At 140x44 it still truncates, at `:logs`.
`Down` and `j`
do not scroll it. The app's best discovery surface is amputated at every size, silently.
Make the panel scroll, or page it, and keep `esc to close` pinned.

The same panel has three smaller faults: `? Keys` and `comma Keys` are listed as two
bindings with one label and no hint they are aliases, `h When` is too clever to read as
the histogram, and `t Trace View` against `shift+t Show Trace` gives two nearly
identical
labels to different actions.

### P1 — An error row is the least legible text on screen

The error row's leading text renders at 3.1:1 against its background, and its trailing
detail text, which is where the status code and the latency live, renders at 1.9:1.
The
ordinary rows around it sit at 4.6:1.
So dimming the continuation of a red row makes the
one row that matters harder to read than every row that does not.
`AGENTS.local.md`
already records this failure mode from the waterfall, and it has reappeared in the log
table.
The severity glyph is doing the real work; the colour is working against it.

### P1 — Charts fill to zero, so most of the plot is ink

`RequestCount` varies between roughly 680 and 1350, and the chart is drawn as a filled
area from zero.
Eighteen of twenty-one plot rows are solid block, and the shape lives in
the top three.
The legend sits inside the plot, over the data.
A line or braille curve
with the axis fitted to the data range would show the incident the demo data contains.

### P1 — The record detail highlights nothing

The pane prints the raw message, then the same payload pretty-printed, both in one flat
colour.
Nothing separates a key from a string from a number, and for a real structlog
record you scroll past a full copy of the payload to reach the readable copy.
Lead with
the parsed view, fold the raw behind a key, and colour it.
Rich's JSON lexer is already in
the dependency tree.

The same pane centres a `Close` button with seven blank rows under it, in an app where
`esc` closes everything, and draws its border in solid `█` where the `?` panel uses
light
box-drawing.
One app, two modal styles.

### P2 — Width is spent backwards

At 80 columns the timestamp column shows `13:11:57`, which is right.
At 120 it expands to
`2026-08-31 13:11:57.702`, spending 25 columns to repeat a date the header already
states
on every row, while the message column is the one that wanted them.
The old critique
killed this exact pattern in the `Log Group` column; it survives in the timestamp.

### P2 — Half the log view is empty

Thirteen events at 120x40 leave twenty blank rows with `Loaded 13 events` floating in
the
middle of them.
The histogram (`h`) and the detail pane (`Enter`) are both good, and both
require knowing they exist.
Filling that space by default, with the histogram or a
persistent detail strip, is the largest available gain in perceived quality and it needs
no new machinery.

### P2 — Silent truncation is back in new places

The log table's own header renders `Timestam`, clipped one character short of
`Timestamp`.
The dashboard sparkline labels read `media`, `sprea`, and `memor` for median,
spread, and memory, which are misleading words rather than visibly shortened ones.
At 40
columns the header ends `logs demo/web-api ·` with a separator and nothing after it,
having dropped the window without saying so.
`report.py:_shorten` is the existing answer.

### P3 — Small findings

Scrollbar fragments bleed into content rows at 40 columns (`▃▃` and `▏` inside the
message
column).
Zebra striping alternates backgrounds by about 4% luminance, which is invisible
and therefore free to remove.
The footer still truncates mid-hint, which the roadmap
already carries as polish.
The histogram headline names a peak time that falls in the
bucket rather than on the event.

### What holds up

The log view reflows properly from 140 down to 40 columns and does not crash: the
timestamp narrows, the message keeps the width, and the severity column stays.
That was
the last critique's P1 and it is fixed.
The severity glyph survives `NO_COLOR`, and
`NO_COLOR` degrades to a greyscale ramp rather than dropping meaning, with the selected
row carried by inversion.
CloudWatch's own vocabulary is used throughout.
The dashboard
grid reflows to the terminal width.

### One gap in the front door

`--demo` covers `logs`, `tail`, and `dash`, but the log group browser is the home screen
and has no offline mode, so the first thing the README tells a reader to run is the one
view they cannot see without an AWS account.

## What not to do

Nothing here argues for a new subsystem, which is the standing risk ADR 0010 names.
The
export items are all functions the cache and DuckDB already provide, exposed at a
boundary that currently discards them.
The terminal items are all corrections to existing
widgets.
The two largest wins, emitting the parsed payload and making the `?` panel
scroll, are both small.
